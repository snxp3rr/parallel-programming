## Используемая задача

Множество Мандельброта визуализируется как растровое изображение размером:

```text
width = 1600
height = 1200
```

Каждый пиксель соответствует комплексному числу. Для каждого пикселя вычисляется количество итераций, за которое значение выходит за некоторый порог, либо максимальное число итераций, если значение остаётся внутри множества.

Формально для комплексного числа `c` итерационный процесс выглядит так:

```text
z_0 = 0
z_{n+1} = z_n^2 + c
```

Если модуль `z_n` превышает 2, точка не принадлежит множеству Мандельброта. Если нет — продолжается до `maxIterations`.

В программе используется функция:

```cpp
mandel(x, y, maxIterations)
```

которая возвращает количество выполненных итераций для конкретной точки.

Главная особенность задачи:

```text
каждый пиксель вычисляется независимо от других пикселей
```

Поэтому задача хорошо подходит для распараллеливания.


### View 2

Увеличенный фрагмент множества Мандельброта:

```text

```

View 2 содержит более сложные области фрактала, поэтому распределение вычислительной стоимости по строкам там ещё более неравномерное.

## Модель параллелизма

Программа использует многопоточность через `std::thread`.

Общая идея:

```text
изображение делится по строкам;
каждый поток вычисляет свою часть строк;
после завершения все потоки объединяются через join();
результат записывается в общий массив output[].
```

Поскольку разные строки матрицы результата не пересекаются, синхронизация между рабочими потоками не требуется.

Единственная необходимая синхронизация — ожидание завершения потоков в функции `mandelbrotThread()` через:

```cpp
workers[i].join();
```

Это не является синхронизацией между рабочими потоками во время вычислений.

## Вариант 1: блочное распределение строк

Первый естественный вариант — разделить изображение на непрерывные блоки строк.

Для `P` потоков поток с идентификатором `threadId` получает строки:

```text
startRow = threadId * height / P
endRow = (threadId + 1) * height / P
```

То есть, например, для 2 потоков:

```text
thread 0: верхняя половина изображения
thread 1: нижняя половина изображения
```

Для 4 потоков:

```text
thread 0: строки 0..299
thread 1: строки 300..599
thread 2: строки 600..899
thread 3: строки 900..1199
```

Этот подход называется spatial decomposition, потому что разные пространственные области изображения обрабатываются разными потоками.

### Проблема блочного распределения

Множество Мандельброта неоднородно. Некоторые области изображения требуют значительно большего количества итераций, чем другие.

Поэтому разные строки изображения имеют разную вычислительную стоимость.

При блочном распределении один поток может получить самый дорогой блок и работать much дольше остальных. В этом случае общее время выполнения определяется не средним временем потоков, а временем самого долгого потока.

Это приводит к плохому ускорению.

Особенно это заметно на 3 потоках, потому что одна из трёх горизонтальных полос может содержать наиболее сложную область фрактала.

---

## Вариант 2: round-robin распределение строк

Чтобы устранить дисбаланс нагрузки, используется более простая и эффективная схема: каждый поток берёт строки по кругу.

Для `P` потоков поток `threadId` обрабатывает строки:

```text
threadId,
threadId + P,
threadId + 2P,
threadId + 3P,
...
```

То есть:

```text
thread 0: 0, P, 2P, 3P, ...
thread 1: 1, P+1, 2P+1, 3P+1, ...
thread 2: 2, P+2, 2P+2, 3P+2, ...
...
```

В коде это выглядит так:

```cpp
for (int row = threadId; row < height; row += numThreads)
{
    mandelbrotSerial(
        args->x0, args->y0,
        args->x1, args->y1,
        width, height,
        row, 1,
        args->maxIterations,
        args->output
    );
}
```

### Почему round-robin лучше

Round-robin не требует синхронизации между потоками.

При этом каждый поток получает смесь дорогих и дешёвых строк. В результате нагрузка распределяется гораздо равномернее.

Общее время выполнения становится ближе к:

```text
T_parallel ~= T_serial / P
```

а не к:

```text
T_parallel ~= max_thread_time
```

где `max_thread_time` — время самого долгого потока.

Именно поэтому round-robin позволяет получить ускорение, близкое к числу аппаратных потоков процессора.

## Методика измерения

Программа `main.cpp` выполняет следующее:

1. Запускает последовательную версию `mandelbrotSerial()` несколько раз.
2. Берёт минимальное время среди прогонов как baseline.
3. Запускает потоковую версию `mandelbrotThread()` несколько раз.
4. Берёт минимальное время среди прогонов.
5. Сравнивает результат потоковой версии с последовательным эталоном.
6. Выводит speedup:

```text
speedup = T_serial / T_threaded
```

Для анализа нагрузки потоков используется переменная окружения:

```bash
PRINT_THREAD_TIMES=1
```

Она включает вывод времени каждого потока, а также:

```text
max thread time
min thread time
avg thread time
max/min imbalance
```

Метрика дисбаланса:

```text
imbalance = max_thread_time / min_thread_time
```

Чем ближе это значение к 1, тем равномернее распределена нагрузка.

## Анализ результатов

### 1. Блочное распределение не даёт линейного ускорения

При блочном распределении каждый поток получает непрерывный диапазон строк изображения.

Однако стоимость вычисления строк неодинакова. Некоторые строки проходят через сложные области множества Мандельброта и требуют гораздо больше итераций.

В результате один поток может работать значительно дольше остальных.

Общее время выполнения параллельной программы определяется самым долгим потоком:

```text
T_parallel ~= max(T_thread_0, T_thread_1, ..., T_thread_P-1)
```

а не средним временем:

```text
T_parallel ~= avg(T_thread_i)
```

Поэтому speedup оказывается ниже идеального.

---

### 2. Особенность трёх потоков

В задании отдельно указано обратить внимание на точку с 3 потоками.

При блочном распределении изображение делится на три горизонтальные полосы. Одна из этих полос может содержать особенно дорогую область фрактала.

Тогда два потока завершают работу быстро, а третий продолжает считать сложный блок. Основные потоки простаивают до завершения самого нагруженного потока.

Именно поэтому на графике speedup для 3 потоков может наблюдаться сильный провал.

---

### 3. Измерение времени потоков подтверждает гипотезу

Времена потоков показывают, что при блочном распределении:

```text
max_thread_time >> min_thread_time
```

То есть дисбаланс нагрузки велик.

После перехода к round-robin времена потоков становятся гораздо ближе друг к другу:

```text
max_thread_time ~= min_thread_time
```

Это означает, что нагрузка распределяется равномерно.

---

### 4. Round-robin улучшает ускорение

Round-robin распределение даёт каждому потоку чередующиеся строки:

```text
0, P, 2P, 3P, ...
1, P+1, 2P+1, ...
2, P+2, 2P+2, ...
```

Таким образом, дорогие и дешёвые строки равномерно распределяются между всеми потоками.

Это простая статическая схема, которая:

- не требует синхронизации между потоками;
- не требует общения между потоками;
- работает для любого количества потоков;
- не требует отдельной настройки под каждый thread count.

Именно это и требовалось в задании.

---

### 5. Ожидаемое ускорение на 8 потоках

На машинах оригинального задания Stanford использовался процессор с 4 физическими ядрами и 8 логическими потоками благодаря Hyper-Threading.

Поэтому целевое ускорение составляло:

```text
около 7–8x на 8 потоках
```

На современной машине с другим количеством ядер и логических потоков ориентир нужно выбирать по числу логических процессоров:

```bash
nproc
```

Если, например, доступно 12 логических потоков, то хороший результат на 8 потоках всё ещё должен быть близок к 7–8x, а на 12 потоках может быть выше.

---

### 6. Поведение при 16 потоках

Запуск с 16 потоками не должен дать заметного прироста по сравнению с количеством аппаратных потоков процессора.

Причина:

- процессор имеет ограниченное число физических ядер;
- операционная система переключает потоки между доступными аппаратными контекстами;
- дополнительные потоки создают накладные расходы на context switching;
- если аппаратных потоков меньше 16, реальный параллелизм не увеличивается пропорционально.

Поэтому performance при 16 потоках обычно:

```text
не заметно выше, чем при числе потоков, равном числу логических ядер
```

или может даже немного ухудшиться.

## Корректность

Программа `main.cpp` автоматически сравнивает результат потоковой версии с результатом последовательной версии:

```cpp
verifyResult(output_serial, output_thread, width, height)
```

Если хотя бы один пиксель не совпадает, выводится ошибка:

```text
Error : Output from threads does not match serial output
```

Во всех проведённых экспериментах результат совпадает, что подтверждает корректность параллельной реализации.
